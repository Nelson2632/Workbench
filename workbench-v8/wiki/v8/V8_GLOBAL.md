# 1. 项目身份

## 1.1 项目名称

**个人工作台 V8 / Personal OS V8**

## 1.2 产品定位

个人工作台不是一个简单的 Todo、笔记或学习软件，而是一个：

> **本地优先、桌面优先、以个人长期信息循环为核心的 Personal OS。**

核心目标不是“功能最多”，而是让用户能够在一个统一系统中完成：

> **计划 → 执行 → 记录 → 数据 → 复盘 → 调整 → 下一次计划**

产品价值来自不同模块之间的联动，而不是模块数量本身。

# 3. 技术基线

当前项目技术栈已经确定，不应为了重构而无理由更换：

- Desktop：Tauri 2.x
- Desktop backend：Rust 2021
- Frontend：React 19.x
- Language：TypeScript 6.x
- Build：Vite 8.x
- Routing：React Router DOM 7.x
- State：Zustand 5.x
- Database：Dexie 4.x / IndexedDB
- Charts：ECharts 6.x
- Styling：CSS Modules
- Notifications：Tauri Notification Plugin
- Global Shortcut：Tauri Global Shortcut Plugin

### 技术原则

1. **本地优先**：业务数据默认存储在本地。
2. **桌面优先但不锁死 Web**：核心前端逻辑不要依赖 Tauri 才能运行。
3. **类型先行**：数据模型在统一类型层定义。
4. **单向数据流**：页面 → Store / Domain → DB → State → 页面。
5. **页面不直接操作数据库**：数据库访问通过 Store / Domain 层完成。
6. **模块解耦**：业务逻辑不能随意跨页面互相调用。
7. **渐进增强**：桌面能力应具备合理的 Web fallback。
8. **优先可维护性**：不为了短期开发速度制造难以维护的巨型组件或跨层逻辑。

# 5. 产品核心闭环

V8 最重要的长期结构：

```text
计划
  ↓
执行
  ↓
记录
  ↓
数据沉淀
  ↓
复盘
  ↓
调整
  ↓
下一轮计划
```

学习系统进一步形成：

```text
知识体系
  ↓
学习
  ↓
错题
  ↓
闪卡
  ↓
复习
  ↓
掌握度
  ↓
学科复盘
  ↓
下一阶段学习计划
```

任何新功能都应该优先回答：

> **它进入了哪一条闭环？它与现有模块如何联动？**

如果一个功能只是“有趣”但无法进入核心循环，应谨慎加入。

# 6. 模块职责边界

这些定义是全局级约束，禁止随意混淆。

## Memo / 备忘录

定义：

> **现在想到、以后再整理的内容。**

特点：快速、轻量、低摩擦。

可转换为：

- 任务
- 笔记
- 错题

备忘录是系统的重要输入接口。

## Note / 笔记

定义：

> **以后还要回来看的长期信息。**

重点是知识沉淀，而不是临时记录。

## Task / 任务

定义：

> **要完成的行动。**

必须有明确行动属性。

## Recurring Task / 周期计划

定义：

> **“这件事情以后会按照规则反复出现”的规则。**

周期计划不是某一天实际执行的任务本身。

关系：

```text
Recurring Rule
    ↓
Generate
    ↓
Task Instance
    ↓
Actual Execution
```

## Project / 项目

定义：

> **为了共同目标而组织的一组任务与里程碑。**

## Knowledge / 知识点

定义：

> **需要掌握的知识节点。**

## Mistake / 错题

定义：

> **已经发生的错误及其原因。**

## Flashcard / 闪卡

定义：

> **用于主动回忆与复习的知识载体。**

## Review / 复盘

定义：

> **理解过去表现，并形成下一阶段调整。**

复盘不是数据展示页，也不是普通日记。

它必须最终导向：

> **下一步行动 / 下一阶段计划。**

# 7. 视觉基线

V8 不使用单一固定视觉主题，而采用“四场景视觉体系”。

## 7.1 A：晨雾书房

用途：

- **白天默认主题**
- 今日
- 计划
- 学习
- 记录
- 普通工作页面

关键词：

> 安静、温润、清爽、书房感、长期耐看。

建议方向：

- 暖白 / 浅灰蓝
- 低饱和强调色
- 柔和阴影
- 适度圆角
- 大留白
- 不追求高信息噪声

## 7.2 C：Windows Fluent

用途：

- 用户手动切换
- 强化 Windows 桌面原生感

原则：

> **Fluent 改变视觉表现，不改变产品信息架构。**

重点可体现在：

- 透明 / 材质感
- Fluent 圆角
- Windows 原生层次
- 更自然的桌面控件表现

不能因为切换 Fluent 而改变页面职责与导航结构。

## 7.3 D：深色夜航

用途：

- **夜间默认主题**
- 夜间学习
- 阅读
- 闪卡
- 专注
- 复盘

关键词：

> 安静、低刺激、沉浸、专注。

不是赛博朋克，也不是纯黑网页。

## 7.4 F：数据驾驶舱

用途：

- 周复盘
- 月复盘
- 考试复盘
- 数据分析类复盘页面

原则：

> **数据驾驶舱只服务于“理解自己”，不扩散到整个工作台。**

普通页面不应全部变成高密度数据面板。

# 8. 自动主题规则

默认支持：

- 自动
- 晨雾书房
- Windows Fluent
- 深色夜航

自动模式建议：

- 白天：晨雾书房
- 夜间：深色夜航

用户可以手动覆盖自动主题。

复盘页的数据驾驶舱是页面级视觉特例，不应理解为第四个全局主题。

---

# 9. 闪卡的全局要求

闪卡是 V8 中允许具有较强视觉识别度的模块。

但必须遵守：

> **背景有氛围，文字永远是第一视觉层。**

至少应支持以下主题方向：

- 晨雾
- 夜空
- 森林
- 琥珀纸页
- 极简

卡片背景原则：

- 可以使用渐变
- 可以使用低强度光晕
- 可以使用轻微噪点 / 纹理
- 可以使用细微图案
- 不应使用喧宾夺主的大图或高对比背景

闪卡必须服务于主动回忆，而不是成为装饰性页面。

---

# 10. 复盘全局要求

复盘体系包含：

- 今日
- 学科
- 周
- 月
- 考试
- 模板

它们不是同一个页面换标题，而是不同粒度的问题解决器：

### 今日复盘

回答：

> 今天发生了什么？今天哪里需要调整？

### 学科复盘

回答：

> 某学科最近学得如何？知识漏洞与错误模式是什么？

### 周复盘

回答：

> 本周整体执行与学习表现如何？下周怎么调整？

### 月复盘

回答：

> 这个月的整体节奏、成果、问题与下一阶段方向如何？

### 考试复盘

回答：

> 这次考试暴露了什么问题？接下来怎么修正？

复盘页面的最后必须存在“下一步”或等价出口，避免复盘成为数据墓地。

# 11. 本地数据与隐私

## 11.1 数据原则

- 默认本地保存
- 默认不要求联网
- 数据可导出
- 数据可恢复
- 数据迁移必须可验证
- 不应无理由将个人数据上传第三方

## 11.2 数据技术

主要业务数据：

> IndexedDB / Dexie

适合结构化、可索引的本地数据。

较大附件、图片、PDF 等后续可以考虑：

> OPFS 或其他合适的本地文件存储方式。

## 11.3 备份

当前策略：

- 每日自动备份
- JSON 格式
- 保留最近 7 份

未来可以增加：

- 手动备份
- 恢复
- 历史备份管理
- 完整性校验

---

# 12. 密码本

密码本是独立的敏感数据区域。

原则：

- 与普通数据逻辑分离
- 普通导出默认不包含密码本
- 密码本继续采用本地加密方案
- 当前方向为 PBKDF2 + AES-GCM

任何 Agent 不得为了方便而把密码本明文并入普通数据流。

---

# 13. V5 → V8 数据兼容

这是重要的不可破坏项。

当前项目已有从 V5 localStorage 数据向 V8 IndexedDB 迁移的设计。迁移要求：

- 尽量保留原有 ID
- 保留已有内容
- 避免重复导入
- 使用事务保证迁移原子性
- 迁移失败不能造成静默数据丢失
- 新版本字段必须考虑旧数据缺失情况

任何数据库结构变更都必须考虑 migration。

# 14. 桌面端能力边界

桌面端应强化“快速进入工作状态”，而不是简单地把网页包成 EXE。

重点能力：

- 快捷备忘
- 全局搜索
- 全局快捷键
- 系统通知
- 系统托盘
- 主窗口快速显示 / 隐藏

未来可以扩展：

- 快速任务
- 自动启动
- 更新机制

但浮动窗口不宜无限增加。

# 15. 全局搜索

全局搜索是 Personal OS 的核心基础设施之一。

搜索范围最终至少包括：

- 任务
- 项目
- 备忘录
- 笔记
- 知识点
- 错题
- 闪卡
- 复盘
- 考试

搜索结果应允许直接跳转到原对象，而不是仅展示文本。

默认快捷键：

> `Ctrl + K`

除非有明确冲突，不应随意修改。

所有快捷键最终应允许在设置中查看与调整。

# 17. UI / UX 总原则

## 原则 1：优先减少功能，而不是增加功能

Windows 已经解决得很好的工具，不要重复建设。

## 原则 2：首页只回答“今天”

首页不是数据仓库。

## 原则 3：一个对象只有一个主要归属

例如：

- 临时内容 → Memo
- 长期知识 → Note
- 行动 → Task
- 规则 → RecurringTask
- 知识 → Knowledge
- 错误 → Mistake
- 回忆训练 → Flashcard
- 反思 → Review

## 原则 4：减少“盒子套盒子”

不是所有内容都需要 Card。

合理区分：

- Section
- List
- Panel
- Card
- Data Block

## 原则 5：视觉层级优先于信息数量

不要为了“展示全面”让首页、学习页或复盘页变成信息墙。

## 原则 6：默认低干扰，交互高效率

尤其是学习、闪卡、阅读、复盘页面。

## 原则 7：桌面端优先，但不破坏 Web 可用性

# 18. 可访问性与响应式

最低要求：

- 键盘可操作
- 明确 focus 状态
- 语义化结构
- 文本与背景有足够对比
- 不仅依靠颜色表达状态
- `prefers-reduced-motion` 下减少动画
- 小屏幕下仍可完成核心任务

桌面端是主体验。

移动端主要保证：

- 查看
- 快速记录
- 基本任务操作

而不是把所有桌面功能无脑压缩到手机屏幕。

---

# 19. 性能原则

不要为了方便在每个页面 `loadAll()` 全部数据。

优先使用：

- 查询型数据加载
- 必要的数据索引
- 派生数据缓存
- 懒加载
- 虚拟列表（在数据规模达到必要程度后）

当前项目已经使用 React.lazy 做路由级懒加载，应保留该原则。

# 21. 文档与开发流程

标准流程：

```text
原项目 + Global Context
        ↓
SPEC
        ↓
PLAN
        ↓
BROWSER / RESEARCH
        ↓
DESIGN REVIEW / 决策整合
        ↓
EXECUTE / CODE
        ↓
TEST
        ↓
REVIEW
```

SPEC 与 PLAN 是不同阶段：

- SPEC：定义“是什么”
- PLAN：定义“怎么做”

BROWSER / RESEARCH：

- 用于补充外部事实
- 用于技术验证
- 用于竞品 / 规范 / 最佳实践研究

不得因为外部产品拥有某功能，就自动推断本项目必须拥有该功能。

# 24. 未来扩展原则

未来任何新模块必须回答四个问题：

1. 它解决了什么现有模块无法解决的问题？
2. 它属于哪个信息对象？
3. 它进入哪条核心闭环？
4. 它是否增加了不必要的认知负担？

如果答案不明确，默认不新增。

# 25. 成功标准

V8 的成功不是“页面更多”或“代码更多”，而是：

### 使用层

用户打开应用后能够快速回答：

> 今天做什么？
> 正在学什么？
> 有什么需要处理？
> 晚上需要复盘什么？

### 学习层

能够看到：

> 学了什么 → 哪里薄弱 → 哪些错题 → 哪些闪卡需要复习 → 下阶段学什么。

### 计划层

能够看到：

> 想做什么 → 什么时候做 → 是否完成 → 为什么没有完成 → 下一次怎么调整。

### 记录层

能够做到：

> 快速记录 → 稍后整理 → 转成正确的信息对象。

### 数据层

能够做到：

> 本地保存 → 可备份 → 可恢复 → 可迁移。

### 桌面层

能够做到：

> 不需要先“打开软件”，就可以通过快捷键快速进入核心动作。

# 26. 给后续 Agent 的一句话

> **不要把 V8 做成一个“功能很多的软件”；要把它做成一个“越来越懂得如何组织我一天、我的学习和我的复盘”的个人操作系统。**

在不破坏数据、安全、技术底座与已确认设计原则的前提下，优先做减法、建立模块之间的连接，并让每一次记录最终能够影响下一次行动。
