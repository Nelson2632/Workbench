# Workbench V9：四个积极性闭环优化计划

> 状态：计划基线（研究与实现待逐项验证）  
> 目标：将“让用户更愿意使用”转化为可验证的产品行为，而不是积分、打卡或提醒堆叠。  
> 动画实验室：[docs/experiments/motion-lab.html](./experiments/motion-lab.html)

## 1. 写入目标

Workbench 是 local-first 的个人操作系统，核心体验应帮助用户把今天过好，并留下值得回看的记录。优化重点不是让用户停留更久，而是降低开始成本、确认真实进展、减少计划失配后的心理负担，并让生活经历自然沉淀为记忆。

本计划建立四个相互衔接的闭环：

1. **Start：低摩擦开始。** 用户能快速从 Today 的当前行动进入实际行动，不必先整理整张任务清单。
2. **Complete：可信的完成反馈。** 只有持久化成功且投影同步后才显示完成反馈，反馈强度与任务意义相称。
3. **Recover：无羞耻地恢复。** 未完成事项提供重新安排、拆分、暂存或放弃等明确出口，不用红色惩罚、连续打卡或“落后”标签施压。
4. **Memory：把经历沉淀为记忆。** 将已完成行动、日记和 LIFE/WORK/PLAY 事件连接成可检索的时间线；回顾可选，不把记录变成额外作业。

## 2. 产品原则与不可破坏的约束

- **Today 是叙事流，不是仪表盘。** 保持 Now → Next → Today Plan：Now 只突出一个当前行动；Next 展示 2–4 项；Today Plan 是完整清单，避免任务重复出现。
- **空间分工清楚。** LIFE / WORK / PLAY 各自承载活动；Review 跨域汇总，不把 Review Data 的密集分析视觉移入 Today。
- **本地优先。** 个人行为数据与评估指标仅在本机计算和保存；不接入将个人数据发送到外部服务的分析 SDK。PDF 导出若实现，必须是用户主动触发、明确选择目的地的独立能力。
- **尊重用户自主权。** 提醒可关闭；计时器可跳过；反思可跳过；不强制积分、排行榜、连续签到或每日空白惩罚。
- **尊重真实作息。** 用户可能学习到 21:30。21:00 提醒（若启用）应指向 Night Shutdown，而非强制 Review；不要将某个固定傍晚时段作为默认的“应该已经完成”判断。
- **事实先于动画。** 完成状态由命令层产生，不由 CSS、点击事件或乐观 DOM 更新产生。
- **单一动效真相来源。** 扩展既有 `v9-motion.css`；不再创建一套重复的通用 duration tokens。主题差异只在确有必要时通过主题作用域变量表达。
- **保留可访问性契约。** `data-v9-done="true"`、`data-v9-done-title`、`data-v9-done-glow="true"` 是受测试保护的契约，不得删除或改名；尊重 `prefers-reduced-motion`。
- **声音不是默认反馈。** 声音最多 P2、用户主动开启、默认关闭；首期可以不做。

## 3. 四个闭环的产品定义

### 3.1 Start：低摩擦开始

**用户问题：** 看见一大堆任务时，不知道先做什么；开始前要填太多字段。

**方案：**
- Now 只放一个当前行动，提供清楚的“开始”主操作。
- 对高启动阻力任务提供可选的“先做 5 分钟”入口。它只是一个低门槛承诺，不代表必须完成 5 分钟，也不强制启动计时器。
- 从 Today / Inbox 开始任务时，默认不要求补齐优先级、标签、时长等非必要字段。
- 开始后只显示必要的上下文与退出方式；计时器是可选工具，不作为任务开始的前置条件。
- 如果 Now 为空，提供从已排定事项中选一个或快速捕获的入口，不制造“今日失败”的空状态。

**验收：** 首次操作路径可由键盘与鼠标完成；启动不要求额外字段；任务开始失败时保留原始内容并给出可理解的错误提示。

### 3.2 Complete：可信的完成反馈

**用户问题：** 完成反馈要么太弱而无感，要么太花哨而失去可信度；写入失败时不能假装完成。

**方案：**
- 命令通过 Mutation Lane 执行，传入稳定的 `commandId`；重复提交必须幂等。
- 只有持久化成功、投影同步完成后，才在 `afterCommit` 发出完成反馈事件。
- 普通任务使用轻量收束；重要里程碑可以有更明显但短暂的反馈；不要给每一次点击都配奖励动画。
- 将既有三个 `data-v9-*` 属性作为 CSS 动效契约。不要以任意 `.done` 类取代契约属性。
- 写入失败时保持真实未完成状态，展示可恢复错误，不触发成功动画，不丢失用户输入。
- Toast 应有按严重程度区分的可读时长并支持 `aria-live`；具体时长以现有实现审计结果和无障碍测试为准，不在本计划中另造第二套 token。

**参考状态机：**
`idle → submitting → committed → projected → feedback`；失败路径为 `submitting → failed → retryable`。重试沿用业务意图但生成/复用 commandId 的规则必须由命令层统一定义，不能由 UI 自行猜测。

### 3.3 Recover：无羞耻地恢复

**用户问题：** 计划与现实总会错位；逾期视觉会让用户回避整个系统。

**方案：**
- 对未完成任务提供明确动作：重新安排、拆小、暂存、放弃。动作含义必须清楚，不能把“暂存”偷偷变成删除。
- 批量延期先预览影响范围，再确认；提供撤销窗口。禁止无预览的“一键延期全部”。
- 逾期状态主要用于提供事实信息，不使用羞辱文案或过度警报色。
- 当日结束时先呈现已经完成的事项与有效记录，再邀请用户处理遗留任务；反思字段可跳过。
- 任何转化或重排失败都保留原事项，展示 pending / success / failure 状态，保证幂等。

**验收：** 用户可在不删除原任务、不丢失输入的前提下完成延期/拆分/暂存；失败可重试；批量操作可撤销或有清楚的恢复机制。

### 3.4 Memory：把经历沉淀为记忆

**用户问题：** 任务完成后就消失，时间线难以表达“这一天发生了什么”。

**方案：**
- 以 Timeline 作为跨域记忆主线，连接任务完成、日记、照片与 LIFE/WORK/PLAY 事件。
- Night Shutdown 先呈现今日成果与已有记录；反思问题可选，不要求用户每天写日记。
- “往年今天”只有在确实存在可展示的本地记录时才出现；没有记录就不显示空壳或虚构内容。
- Review 用于周期性回看与跨域理解，不强行塞入 Today 的主流程。
- 所有回顾、统计与推荐均基于本地数据；提供关闭/隐藏个别模块的能力。

**验收：** 记忆卡片可回到对应原始记录；缺少数据时优雅隐藏；删除或编辑原始记录后，相关投影可按现有投影架构一致更新。

## 4. 四闭环之间的连线

```text
Start ──开始行动──> Complete ──留下可信事实──> Memory
  ^                     │                         │
  │                     v                         │
  └──── Recover <── 未完成/计划失配 <──────────────┘
```

这不是必须每天完整跑完的漏斗。用户可以只捕获、不开始；可以完成、不反思；也可以随时退出。系统不能把闭环完整率当作用户价值或绩效分数。

## 5. 事件与工程契约（实现前必须对照现有代码）

- **Command 层：** 所有状态变更通过现有 `runCommand` / Mutation Lane；每个变更有稳定的 `commandId` 和明确的失败结果。
- **持久化层：** 先提交事实，再更新/确认投影；不能由视图直接改写事实或投影。
- **反馈层：** `afterCommit` 只在提交成功且投影同步后执行。反馈消费端应对 commandId 去重，避免重放、重渲染或多订阅者导致重复动画。
- **CSS 层：** 复用 `v9-motion.css` 中既有的 `data-feedback` 与 `data-v9-done*` 契约；主题只改变材质表现，不改变成功/失败的语义。
- **无障碍：** 动画不是唯一状态信号；状态变化应有文本或语义属性；减少动态效果时仍可理解反馈。
- **数据层：** 本地指标优先派生计算；如需持久化事件，先检查现有事实表/投影是否已经覆盖，避免新增重复存储。

## 6. 本地评估指标

这些指标用于判断交互是否减少摩擦，不构成用户评分，也不上传：

| 闭环 | 指标 | 解释边界 |
|---|---|---|
| Start | 从 Today 展示到开始命令成功的中位时间；开始前取消率 | 不以“越快越好”单独评判，需结合任务类型 |
| Complete | 成功提交后反馈出现延迟；重复反馈率；提交失败时误显示成功次数 | 误显示成功目标为 0 |
| Recover | 延期/拆分/暂存操作完成率；撤销率；恢复后再次打开该任务的比例 | 撤销率高可能表示预览不清，不直接视为负面 |
| Memory | 记忆条目回看率；由记忆条目返回原记录的比例；用户主动隐藏模块的比例 | 不把日记字数、连续天数作为目标 |
| 全局 | 命令失败率、丢失输入次数、重复命令次数、减少动效偏好生效情况 | 默认仅本机可见；提供清除诊断指标的方式 |

首期应先实现可靠性指标与人工可用性走查，再决定是否保留更多统计。不要为追求指标而增加外部遥测。

## 7. 实施路线图

### Phase 0：审计与基线
- 检查 `workbench-v8` 中 Today、任务命令、Mutation Lane、投影同步、EventBus、Night Shutdown、Timeline、`v9-motion.css` 与 `a11yPolicy.test.ts` 的真实实现。
- 记录现有测试基线与已知失败；区分代码事实、历史问题与待验证假设。
- 先确认当前 `data-v9-*` 属性从状态到 DOM 的完整路径。

### Phase 1：可靠性优先
- 修复完成反馈与持久化提交顺序、commandId 幂等和投影同步。
- 为快速添加、Inbox 转化等异步路径保留输入，补齐 pending / success / failure 状态。
- 为反馈增加可访问语义和减少动态效果测试。
- 验收：失败不出现成功态；重复命令不重复写入/动画；既有契约测试通过。

### Phase 2：Start + Recover
- 优化 Now 单一当前行动、快速开始与可选 5 分钟入口。
- 为未完成任务提供重新安排、拆分、暂存、放弃等清楚动作。
- 批量延期实现预览、确认与撤销；禁止静默丢弃原任务。
- 验收：不新增强制字段；失败保留内容；原任务与新任务关系可追踪。

### Phase 3：Memory + Night Shutdown
- 整合现有 Timeline / Daily Memory 投影，展示真实完成成果。
- 将反思设为可选；21:00（用户启用提醒时）指向 Shutdown，不强制 Review。
- “往年今天”只在有真实数据时显示。
- 验收：无数据不显示虚构内容；返回原记录可用；投影重建一致。

### Phase 4：主题动效与评估
- 将四主题动效与现有 `v9-motion.css` 对齐；以动画实验室进行视觉验收。
- 核对所有动效时长来源，避免重复的通用 token。
- 在本机计算少量可靠性/摩擦指标，确认不会出网。
- 验收：四主题有清晰材质差异；Reduced Motion 有效；无外部分析请求。

## 8. 测试矩阵

| 场景 | 预期结果 |
|---|---|
| 完成命令持久化失败 | 不设置完成属性、不播成功动画、保留真实状态并允许重试 |
| 同一 commandId 重放 | 事实不重复写入，成功反馈不重复 |
| 投影延迟或失败 | 在投影一致前不触发完成反馈；错误可观测 |
| React 重渲染/页面恢复 | 不因重新挂载重播旧完成动画 |
| 用户启用 Reduced Motion | 不依赖动画传达成功/失败 |
| 快速添加写入失败 | 输入仍在，显示错误与重试 |
| 批量延期 | 先预览，确认后执行；支持撤销/恢复 |
| Night Shutdown 无任务完成 | 不指责用户；允许结束流程或可选记录 |
| Timeline 无历史记录 | 隐藏“往年今天”，不显示空卡片 |
| 离线运行 | 核心功能正常，无遥测请求 |
| LIFE / WORK / PLAY 任务 | 状态与事实归属正确，Review 可跨域回看 |
| 键盘与屏幕阅读器 | 主要动作可操作，状态变化有语义反馈 |

## 9. 完成定义

一个闭环只有同时满足以下条件才算完成：
1. 用户路径已实现，而不只是静态视觉稿。
2. 成功与失败状态均有明确行为，输入与原始事实不会意外丢失。
3. 关键契约有自动化测试，涉及命令、投影和动画的部分有集成测试。
4. 键盘、屏幕阅读器和 Reduced Motion 路径可用。
5. 不向外部发送个人行为数据。
6. 文档、实现和测试结果一致；报告实际通过/失败，不用“看起来正常”代替验证。
